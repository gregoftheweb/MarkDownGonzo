## Priority 1: recurring WebKitWebProcess shutdown crash — RESOLVED 2026-08-30

### Root cause (confirmed)

Every `WebKitWebProcess` coredump has an identical stack. Unsymbolized but unambiguous:

```text
WebKitWebProcess main
  -> __libc_start_main
  -> exit
  -> __run_exit_handlers
  -> <atexit handler in libwebkit2gtk-4.1.so.0 +0x4492fea / +0x449317b>
  -> <libwebkit2gtk-4.1.so.0 +0x180b199>            (DMABUF renderer / GBM device teardown)
  -> libgbm.so.1  gbm_device_destroy
  -> dri_gbm.so   backend destroy
  -> glibc allocator -> SIGSEGV (SEGV_MAPERR)
```

On exit the WebKit **web content** process runs an atexit handler that destroys the
DMABUF renderer's GBM device. Mesa's GBM/DRI backend faults in the glibc allocator
because the underlying DRI state is already torn down (use-after-free / double-free
during static destruction ordering). The crash happens in the child process after
our window is already gone, so the only visible symptom is the systemd-coredump
notification. This is a WebKitGTK + Mesa bug; nothing in MarkDownGonzo's Tauri code
runs on that teardown path, so there is no application-level lifecycle fix.

Environment where reproduced: Intel UHD 620 (WhiskeyLake-U), Mesa 26.1.8,
webkit2gtk-4.1 2.52.6, Hyprland/Wayland.

### A/B test (installed `0.1.0-2`, opening a real Markdown file, close via SIGTERM)

| Configuration | WebKitWebProcess coredumps / exits |
| --- | --- |
| Baseline (no override) | 8 / 47  (~17%) |
| `WEBKIT_DISABLE_DMABUF_RENDERER=1` | 0 / 30 |
| Fixed release binary, **no** env override | 0 / 20 |

The synthetic ~17% rate is lower than the "nearly every exit" seen in interactive
dev sessions (longer-lived windows accumulate more renderer state), but the crash
signature is identical and the mechanism is the same. `WEBKIT_DISABLE_DMABUF_RENDERER=1`
makes WebKit use the SHM compositing path, which never creates the GBM device, so
the faulty teardown never runs. GPU compositing is not needed for this editor.

`WEBKIT_DISABLE_COMPOSITING_MODE=1` was not needed and was not applied.

### Fix

`src-tauri/src/lib.rs` — `apply_webkit_shutdown_workaround()` is called at the top of
`run()`, before `tauri::Builder`, so the variable is set before the WebView (and its
web process) is created:

```rust
#[cfg(all(desktop, target_os = "linux"))]
fn apply_webkit_shutdown_workaround() {
    if std::env::var_os("WEBKIT_DISABLE_DMABUF_RENDERER").is_none() {
        std::env::set_var("WEBKIT_DISABLE_DMABUF_RENDERER", "1");
    }
}
```

- Linux + desktop only.
- Respects an explicit user/distributor override (only sets the var if unset).
- `set_var` is safe here: single-threaded, called first thing in `main` -> `run`,
  crate is edition 2021.
- Confirmed at runtime that the variable propagates into the spawned
  `WebKitWebProcess` environment.

Verified via the propagation check plus `strings` on the packaged binary.

### Data-loss assessment (unchanged)

not Markdown documents. Unsaved editor content remains a separate lifecycle concern;
the crash does not prove unsaved state is safe, but it also does not threaten it.

## Window title bar removed on Linux (2026-08-30)

Omarchy/Hyprland provides no server-side title bar, so GTK was drawing its own
client-side one (centered title + minimize/maximize/close) above the app's own
header. Those buttons are redundant on Hyprland — move is Super+drag, close is
Super+Q, tiling/resize is compositor-managed — and the app already has its own
top bar with the document tabs and controls.

The window is now undecorated:

- `src-tauri/tauri.conf.json`: `"decorations": false` on the main window.
- `src-tauri/src/lib.rs`: `apply_window_decorations()` also calls
  `window.set_decorations(false)` from the Tauri `setup` hook. This is required —
  config-only `decorations: false` was **not** honored by GTK on Wayland in
  testing (tao 0.35.3 / webkit2gtk 2.52.6); the title bar still appeared. The
  runtime call removes it reliably. Verified with a screenshot on Hyprland.
- Linux-only (`#[cfg(all(desktop, target_os = "linux"))]`). If the app is ever
  ported to macOS/Windows, give those platforms a normal title bar (they have no
  compositor-level window controls).

## Important packaging history

The first native package, `0.1.0-1`, was incorrectly built without Tauri's `custom-protocol` feature. Its binary attempted to load the Vite development URL at `http://localhost:1420` and displayed “Connection refused” when launched outside the development server.

This was permanently corrected in `src-tauri/Cargo.toml`:

```toml
[features]
default = ["custom-protocol"]
custom-protocol = ["tauri/custom-protocol"]
```

Tauri development continues to work because `tauri dev` explicitly invokes Cargo with `--no-default-features`. Normal release builds now embed the frontend assets. Package revision `0.1.0-2` was built cleanly, confirmed to contain the production JavaScript asset, launched directly for a runtime smoke test, installed through Pacman, and manually approved by the user.

Package revision `0.1.0-3` (2026-08-30) bundles three changes; `pkgrel` bumped
2 -> 3, no version change:

1. WebKit shutdown-crash workaround (`src-tauri/src/lib.rs`).
2. Undecorated window on Linux (`src-tauri/src/lib.rs` + `decorations: false` in
   `tauri.conf.json`).
3. ODT/PDF export (`src-tauri/src/export.rs`, `export_document` command, frontend
   wiring). Adds `optdepends` on LibreOffice for PDF. New Rust deps:
   `pulldown-cmark`, `flate2` (both offline-cached).

Do not remove or bypass the `custom-protocol` default feature in release packaging.

## Priority 2: ODT and PDF export — IMPLEMENTED 2026-08-30

Shipped in package revision `0.1.0-3`. New module `src-tauri/src/export.rs`, one
Tauri command `export_document`, frontend wiring in `App.tsx` / `backend.ts`.

### Behaviour

- Export menu in the tab-row actions (icon: `FileDown`), with **Export to PDF…**
  and **Export to ODT…**. Keyboard: `Ctrl+Shift+E` opens it (first item focused,
  arrow keys navigate).
- Native save dialog, extension/filter per format, default name derived from the
  document name (`exportFileName`: strips `.md`/`.markdown`, appends `.odt`/`.pdf`).
- The command receives `{ markdown, destination, documentDir, title }` and never
  touches the open document — no save, no dirty flag, no autosave interaction. It
  only reads `activeTab.content`.
- Success and failure both show a transient banner above the editor; the source
  document is never modified or dirtied.
- Leading YAML frontmatter is treated as metadata: not rendered, but a `title:`
  line feeds the document metadata.

### ODT — self-contained, pure Rust

Markdown (`pulldown-cmark`, GFM options) → ODF XML → zip (hand-rolled minimal ZIP
writer over `flate2`; `mimetype` stored first). No external tools. Covers:
headings, bold/italic/strikethrough/inline-code, links, bullet/ordered/nested
lists, task lists (☑/☐), GFM tables with per-column alignment and a bold header
row, `[!NOTE]`-style alert callouts, blockquotes, fenced code blocks (indentation
and blank lines preserved), thematic breaks, footnotes (real `<text:note>`),
images (embedded into `Pictures/`, dimensions read from PNG/JPEG/GIF/WebP/SVG
headers, scaled to the page width), and the documented `<u>` HTML underline.
Relative images resolve against `documentDir`; remote/missing images fall back to
their alt text so nothing is silently dropped.

### PDF — LibreOffice, optional dependency

The generated ODT is handed to `soffice --headless --convert-to pdf` in a private
`UserInstallation` profile (safe alongside a running LibreOffice), with a 120 s
timeout, then moved to the destination with `atomic_write`. LibreOffice is
detected on `PATH` (`soffice`, `libreoffice`) plus common fallback paths. If it is
missing the command returns `CommandError::DependencyMissing` and the UI shows a
quirky actionable message ("…if you want a PDF you're gonna need LibreOffice.
Install it (Arch: sudo pacman -S libreoffice-fresh) — or export to ODT instead").
On plain Arch without LibreOffice, ODT export still works.

`PKGBUILD` gains `optdepends=('libreoffice-fresh: PDF export' ...)` — see below.
