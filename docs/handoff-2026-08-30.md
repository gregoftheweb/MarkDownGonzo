## Priority 1 tomorrow: recurring WebKitWebProcess shutdown crash

Fix or mitigate this before starting ODT/PDF export.

### Observed evidence

- `coredumpctl list` showed 10 `WebKitWebProcess` coredumps on 2026-08-29 alone.
- They clustered around the 12:11–13:52 development/test session and the final packaging test.
- A representative crash occurred at 22:22:06. The user upgraded the package at 22:22:31 and relaunched at 22:22:38, tightly correlating the crash with quitting the prior app instance for the rebuild.
- The preview subprocess, rather than the main `markdowngonzo` process, is what segfaults.
- The behavior recurs on essentially every exit. The visible symptom is a coredump notification after the application is already gone.
- This is not presently attributed to Omarchy. Omarchy ships neither MarkDownGonzo nor the relevant WebKitGTK/Mesa behavior.

### Data-loss assessment

No data loss is attributable to the observed subprocess crashes. The WebKit data directory at `~/.local/share/com.columbiafoundry.markdowngonzo/` contains browser cache/storage rather than Markdown documents. Nothing was deleted and there is nothing crash-related to recover from trash.

Unsaved editor content remains a separate application-lifecycle concern. Confirm that the normal save/session logic finishes before shutdown; do not assume the subprocess crash proves that unsaved state is safe.

### Leading hypothesis and diagnostic plan

The leading hypothesis is a WebKitGTK/Mesa GBM renderer teardown fault during application shutdown. That is an inference until confirmed by controlled tests.

1. Establish a baseline by launching and closing the installed release several times, then compare the `WebKitWebProcess` coredump count and timestamps.
2. Repeat with `WEBKIT_DISABLE_DMABUF_RENDERER=1`. If crashes stop, this strongly implicates the GBM/DMABUF path.
3. If needed, repeat separately with `WEBKIT_DISABLE_COMPOSITING_MODE=1` to test the broader GPU-compositing path.
4. Inspect MarkDownGonzo/Tauri shutdown behavior. Ensure the window and WebView are dropped cleanly and the GTK main loop is allowed to unwind; look for any direct process termination or premature exit path.
5. Use `coredumpctl info` and, if needed, a temporary symbolized core following the `diagnose-crash` skill. Never retain or commit extracted cores because they can contain private document data and credentials.
6. Re-test repeated exits in both development and installed release builds.

Preferred fix: correct application/WebView teardown if MarkDownGonzo controls the faulty lifecycle. Acceptable packaging workaround: set `WEBKIT_DISABLE_DMABUF_RENDERER=1` for the launched application if the A/B test confirms the renderer path and no clean application-level fix is available. GPU compositing is not essential for this Markdown editor.

Acceptance criterion: repeated normal exits produce no new `WebKitWebProcess` coredumps while document saving and session restoration continue to work. If a minimal correctly-shutting-down Tauri application reproduces the crash, prepare an upstream WebKitGTK report with sanitized diagnostics rather than reporting it to Omarchy.

## Important packaging history

The first native package, `0.1.0-1`, was incorrectly built without Tauri's `custom-protocol` feature. Its binary attempted to load the Vite development URL at `http://localhost:1420` and displayed “Connection refused” when launched outside the development server.

This was permanently corrected in `src-tauri/Cargo.toml`:

```toml
[features]
default = ["custom-protocol"]
custom-protocol = ["tauri/custom-protocol"]
```

Tauri development continues to work because `tauri dev` explicitly invokes Cargo with `--no-default-features`. Normal release builds now embed the frontend assets. Package revision `0.1.0-2` was built cleanly, confirmed to contain the production JavaScript asset, launched directly for a runtime smoke test, installed through Pacman, and manually approved by the user.

Do not remove or bypass the `custom-protocol` default feature in release packaging.

## Native Arch package

Build from the application directory:

```bash
./scripts/build-arch-package.sh
```

Current output:

```text
packaging/arch/markdowngonzo-0.1.0-2-x86_64.pkg.tar.zst
```

Install or upgrade:

```bash
sudo pacman -U packaging/arch/markdowngonzo-0.1.0-2-x86_64.pkg.tar.zst
```

The package installs:

- `/usr/bin/markdowngonzo`
- Freedesktop desktop entry
- 32, 64, 128, and 256-pixel hicolor icons
- AppStream metadata
- Markdown MIME registration

The package is approximately 3.6 MiB compressed and 10.3 MiB installed. Runtime dependencies are `webkit2gtk-4.1` and `gtk3`.

The local Node/npm installation is not owned by Pacman, so the build wrapper validates the tools directly and passes `--nodeps` to `makepkg`. The `PKGBUILD` still declares correct build dependencies for clean Arch/AUR builders.

## Priority 2 tomorrow: ODT and PDF export

The user wants both Export to ODT and Export to PDF added next.

Treat export as a document feature, not as Save As: the source Markdown document, path, dirty state, and autosave behavior must remain unchanged after export.

Recommended workflow:

1. Add an Export action to the document UI, with separate “OpenDocument Text (.odt)” and “PDF (.pdf)” choices.
2. Use native save dialogs with the appropriate extension/filter and sensible defaults derived from the document name.
3. Define a narrow Tauri command boundary that receives source Markdown plus an explicit destination path.
4. Preserve headings, emphasis, links, lists, blockquotes, code blocks, tables, and images. Resolve relative images against the Markdown document directory before conversion.
5. Report conversion failures in the UI without altering or dirtying the source document.
6. Add focused unit/integration coverage and manually compare exported output against a representative Markdown fixture.

Before choosing an implementation, check what is available on plain Arch and decide whether exports must work with no optional external executable. A self-contained implementation is preferable for predictable installation. If Pandoc or LibreOffice is used, make it an explicit optional dependency, detect it cleanly, and present an actionable error. Do not silently shell out to an undeclared tool.

For PDF, evaluate whether Tauri/WebKitGTK printing can produce a dependable file directly. If not, use the same documented conversion layer selected for ODT. The exported PDF should reflect rendered Markdown rather than raw source text.
