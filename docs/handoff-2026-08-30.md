## Change 1: WebKitWebProcess shutdown crash — FIXED

### Root cause (confirmed)

Every `WebKitWebProcess` coredump had an identical stack (unsymbolized but
unambiguous):

```text
WebKitWebProcess main
  -> __libc_start_main -> exit -> __run_exit_handlers
  -> <atexit handler in libwebkit2gtk-4.1.so.0>
  -> DMABUF renderer / GBM device teardown
  -> libgbm.so.1  gbm_device_destroy
  -> dri_gbm.so   backend destroy
  -> glibc allocator -> SIGSEGV (SEGV_MAPERR)
```

On exit the WebKit web-content process runs an atexit handler that destroys the
DMABUF renderer's GBM device; Mesa's GBM/DRI backend faults in the allocator
because the DRI state is already torn down (static-destruction-order
use-after-free). The crash is in the child process after the window is gone, so
the only symptom is a systemd-coredump notification. It is a WebKitGTK + Mesa
bug — nothing in the app's Tauri code runs on that path, so there is no
application-level lifecycle fix.

Reproduced on: Intel UHD 620 (WhiskeyLake-U), Mesa 26.1.8, webkit2gtk-4.1 2.52.6,
Hyprland/Wayland.

### A/B test

| Configuration | WebKitWebProcess coredumps / exits |
| --- | --- |
| Baseline `0.1.0-2`, no override | 8 / 47 (~17%) |
| `WEBKIT_DISABLE_DMABUF_RENDERER=1` | 0 / 30 |
| Fixed release binary, no env override | 0 / 20 |

The synthetic ~17% is lower than the "nearly every exit" of interactive sessions
(longer-lived windows accumulate more renderer state), but the signature is
identical. Disabling the DMABUF renderer makes WebKit use SHM compositing, which
never creates the GBM device, so the faulty teardown never runs. GPU compositing
is not needed for this editor. `WEBKIT_DISABLE_COMPOSITING_MODE=1` was not needed.

### Fix — `src-tauri/src/lib.rs`

`apply_webkit_shutdown_workaround()` sets `WEBKIT_DISABLE_DMABUF_RENDERER=1` at
the top of `run()`, before `tauri::Builder`, so it is set before the WebView (and
its web process) is created.

- Linux + desktop only.
- Only sets the var if unset — respects a user/distributor override.
- `set_var` is safe: single-threaded, first thing in `main` -> `run`, edition 2021.
- Verified at runtime that the var propagates into the spawned `WebKitWebProcess`.

### Data-loss assessment

No data loss is attributable to the subprocess crashes — the WebKit data dir
(`~/.local/share/com.columbiafoundry.markdowngonzo/`) holds cache/storage, not
documents. Unsaved editor content is a separate lifecycle concern; the crash
neither proves it safe nor threatens it.

### Diagnostic hygiene

- The temporarily extracted ~6 GB core was deleted; no core retained or committed.
- Test runs on 2026-08-30 generated ~40 `WebKitWebProcess` coredumps (systemd
  keeps the most recent ~25). Optional cleanup:
  `sudo rm /var/lib/systemd/coredump/core.WebKitWebProces.*.zst`
- A symbolization attempt pulled ~2.3 GB into `~/.cache/debuginfod_client` —
  harmless, self-managing, safe to clear.

### If it recurs

Prepare a WebKitGTK bug report (bugs.webkit.org) with a minimal Tauri/WebKitGTK
reproducer and sanitized `coredumpctl info`. Do **not** report to Omarchy — it
ships neither this app nor the WebKitGTK/Mesa stack.

## Change 2: undecorated window on Linux

Hyprland provides no server-side title bar, so GTK drew its own client-side one
(centered title + min/max/close) above the app's own header. Those are redundant
under Hyprland (move: Super+drag, close: Super+Q, tiling: compositor-managed).

- `src-tauri/tauri.conf.json`: `"decorations": false` on the main window.
- `src-tauri/src/lib.rs`: `apply_window_decorations()` also calls
  `window.set_decorations(false)` from the `setup` hook — **required**, because
  config-only `decorations: false` was not honored by GTK on Wayland in testing
  (tao 0.35.3 / webkit2gtk 2.52.6); the title bar still appeared. Verified gone
  via screenshot on Hyprland.
- Linux-only. If ported to macOS/Windows, give those a normal title bar.

## Change 3: ODT and PDF export

New module `src-tauri/src/export.rs`, one command `export_document`, frontend
wiring in `App.tsx` / `backend.ts`.

### Behaviour

- Export menu in the tab-row actions (`FileDown` icon): **Export to PDF…** /
  **Export to ODT…**. `Ctrl+Shift+E` opens it (first item focused, arrow keys
  navigate).
- Native save dialog, extension/filter per format, default name from the document
  name (`exportFileName` strips `.md`/`.markdown`, appends `.odt`/`.pdf`).
- Command receives `{ markdown, destination, documentDir, title }` and **never
  touches the open document** — no save, no dirty flag, no autosave interaction;
  it only reads `activeTab.content`.
- Success and failure both show a transient banner above the editor.
- Leading YAML frontmatter is treated as metadata: not rendered; a `title:` line
  feeds the document metadata.

### ODT — self-contained, pure Rust

Markdown (`pulldown-cmark`, GFM options) → ODF XML → zip (hand-rolled minimal ZIP
writer over `flate2`, `mimetype` stored first). No external tools. Covers:
headings, bold/italic/strikethrough/inline-code, links, bullet/ordered/nested
lists, task lists (☑/☐), GFM tables with per-column alignment and a bold header
row, `[!NOTE]` alert callouts, blockquotes, fenced code (indentation and blank
lines preserved), thematic breaks, footnotes (real `<text:note>`), embedded
images (dimensions read from PNG/JPEG/GIF/WebP/SVG headers, scaled to page
width), and the documented `<u>` HTML underline. Relative images resolve against
`documentDir`; remote/missing images fall back to alt text so nothing is silently
dropped.

### PDF — LibreOffice, optional dependency

The generated ODT is handed to `soffice --headless --convert-to pdf` in a private
`UserInstallation` profile (safe alongside a running LibreOffice), 120 s timeout,
then moved to the destination with `atomic_write`. LibreOffice is detected on
`PATH` (`soffice`, `libreoffice`) plus common fallback paths. If missing, the
command returns `CommandError::DependencyMissing` and the UI shows a quirky
actionable message; ODT export still works. `PKGBUILD` gains `optdepends` on
`libreoffice-fresh` / `libreoffice-still`.

### Tests

- `src-tauri/src/export.rs` unit tests (14): heading/inline marks, link + XML
  escaping, nested lists + tasks, ordered list, table header + alignment, code
  block indentation, blockquote + alert, `<u>`, frontmatter stripping + title
  extraction, missing-image alt fallback, embedded-image packaging, image header
  dimension readers, ZIP structure, footnotes → notes.
- `#[ignore]` `libreoffice_accepts_generated_odt`: renders a representative
  fixture through the real ODT writer + LibreOffice and asserts a valid PDF.
  `cargo test -- --ignored`. `MDG_EXPORT_DUMP=/path/prefix` keeps the artifacts.
- `src/exportName.test.ts` (4): `exportFileName`.
- Verified visually: the fixture PDF renders headings, marks, callout, lists,
  aligned table, shaded code block, rule, and footnote correctly (pdftoppm).

### Also in this change

Tab-row layout reworked: the find / export / save actions stay pinned while the
tab list scrolls. Previously they were pushed off-screen with several tabs open.

## Known issues / follow-ups

- **Footnotes / MDX / JSX / math block the Visual editor.** `visualSafetyWarnings()`
  in `markdown.ts` forces those documents into Raw mode to avoid a lossy
  round-trip. Export handles footnotes fine (real ODF notes). Adding a TipTap
  footnote node + markdown serialization so those docs open in Visual mode is a
  reasonable standalone task if the owner wants it.
- **AppImage** bundling is enabled in `tauri.conf.json` but `linuxdeploy` fails on
  this Omarchy/Arch host (only the final bundling step; the binary builds).
  Diagnose before a v1.0 GitHub release if AppImage distribution is wanted:
  `npm run tauri -- build --bundles appimage --verbose`.
- **WebP lossless (`VP8L`)** image dimensions fall back to a default size in the
  ODT exporter (VP8X and lossy VP8 are handled).
- **Export save-dialog E2E** was not automated — Hyprland focus-stealing by the
  agent terminal blocked `wtype` into the GTK dialog. The dialog was confirmed to
  open with the correct name/filter; the command body is covered by the
  `#[ignore]` LibreOffice test.
- The installed `0.1.0-3` predates the MIT metadata change (see Package section).
